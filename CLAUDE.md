## Stack & Conventions

**Hard constraints — do not violate these:**

1. **Single-file project.** The entire project must live in one `index.html` file, with all CSS and JavaScript inlined directly in that file using `<style>` and `<script>` tags — never in separate `.css` or `.js` files, and never split across multiple HTML pages. Linking external images, CSS libraries, and JavaScript libraries (e.g. via `<link>`/`<script src>` to a CDN) is allowed. No additional pages of any kind. This constraint exists so the finished project can be copy-pasted as a single file for sharing in class and on single-file code platforms (e.g. CodePen, JSFiddle).
2. **Vanilla only.** Use plain HTML, CSS, and JavaScript only. No frameworks or libraries that require a build step (no React, Vue, TypeScript, Sass, JSX, bundlers, etc.), and no build/compile step of any kind. The file must run as-is when opened directly in a browser.

## Tech stack (hard constraints — do not deviate)
- Vanilla HTML, CSS, and JavaScript only. No React, Vue, or any JS framework.
- Tailwind CSS for all styling (via CDN only).
- No backend, no database. Fully static site.
- A toggle for light and dark theme, with the choice remembered
  across visits.

## Feature Plan

A web portal where visitors browse and try a growing collection of small
web tools and learning artifacts. Built incrementally in phases; each
phase should stay small enough to prove the pattern without building the
whole collection at once.

As phases are completed, mark them done (e.g. strike through or note
"✅ done") or prune finished implementation detail down to a one-line
summary, so this section stays skimmable as the collection grows.

### Data model

```js
// One entry per tool/artifact in the collection.
{
  id: 'word-counter',       // unique slug, used as view key
  title: 'Word & Character Counter',
  description: '...',       // shown on gallery card
  category: 'tool' | 'learning',
  render: (container) => {} // mounts the tool's markup/logic into container
}

const TOOLS = [ /* ...entries above... */ ];
```

Gallery cards and the view-switcher are both generated by looping over
`TOOLS` — adding a new tool later means appending one entry (plus its
markup/logic), with no changes needed to the gallery or switcher.

### Key flows

- **Gallery → tool**: clicking a tool card hides the gallery, shows that
  tool's container, and calls its `render()`. A "← Back to tools" control
  reverses this. Plain JS show/hide — no URL/hash routing, no separate
  pages.
- **Theme toggle**: light/dark applied via a root class + Tailwind `dark:`
  variants; choice saved to `localStorage` and applied on load before
  paint (avoid flash of wrong theme).

### Phase 1 — prove the pattern (two entries)

Scope: shell (header incl. theme toggle, gallery, view-switcher) + exactly
two entries, one per category.

- Shell: header with site title + theme toggle, gallery view, tool view
  container, footer.
- Tool registry (`TOOLS` array) + gallery rendering + view-switcher, per
  data model/flows above.
- Entry 1 (`category: 'tool'`) — **Word & Character Counter**: textarea
  input; live word / character / character-without-spaces / sentence
  counts on input.
- Entry 2 (`category: 'learning'`) — **Quick Quiz**: small hardcoded
  multiple-choice question set, one question at a time, instant
  right/wrong feedback, running score, restart at end. No persistence —
  resets on reload.
- Theme toggle wired to `localStorage`.

### Phase 2+ — grow the collection (not yet planned in detail)

- Add further tools/learning artifacts as new `TOOLS` entries.
- Revisit only if phase 1 reveals the registry pattern needs to change
  (e.g. filtering/search across categories once the list grows long).
